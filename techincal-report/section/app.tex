This section presents \emph{Who-Speak-AI}, an end-to-end conversational virtual assistant that integrates our fine-tuned RawNet3 speaker verification model into a modular, privacy-preserving voice pipeline.

\subsubsection{User Interface}

The presentation layer comprises a production web client and an offline diagnostic dashboard:
\textbf{Production Web Application (\texttt{app/web}):} Built with React 19, TypeScript 5.7, Vite 7, and Vanilla CSS (dark-mode, glassmorphism). The UI coordinates four core functions: (1) \emph{Coordinator} for registration, login (\texttt{scrypt}, \texttt{HttpOnly} cookies), and 3-sample voice enrollment; (2) \emph{Voice Stage} rendering an animated orb tracking RMS audio energy across states (\emph{Idle}, \emph{Listening}, \emph{Thinking}, \emph{Speaking}, \emph{Challenging}); (3) \emph{Conversation Feed} displaying streaming transcripts, authorization badges, tool receipts, and biometric challenge modals; and (4) \emph{Hardware Telemetry} managing I/O devices and WebRTC status.
\textbf{Client-Side Audio Engineering:} Audio is captured via Web Audio API, downmixing to mono 16-bit linear PCM at 16~kHz. Full-duplex WebRTC streaming is handled by \texttt{livekit-client} 2.22.0 across topics \texttt{voice-auth}, \texttt{voice-auth-status}, \texttt{voice-agent-event}, and \texttt{voice-agent-command}.
\textbf{Diagnostic Dashboard:} A Streamlit app for offline 1:1/1:N verification, waveform/spectrogram inspection, and ROC/DET calibration.

\subsubsection{Runtimes}

\textbf{System \& Media Transport:} Python 3.12 backend and Node.js frontend. Media routing is handled by \textbf{LiveKit Server} (SFU) with 16~kHz mono PCM ingress and 48~kHz mono PCM egress in the Pipecat transport layer.
\textbf{Conversational Pipeline (Pipecat):} Orchestrated by \textbf{Pipecat} in a framed asynchronous flow:
\begin{equation}
\begin{aligned}
    \text{LiveKit In} &\longrightarrow \text{AuthRouter} \longrightarrow \text{VAD} \longrightarrow \text{Smart Turn} \\
    &\longrightarrow \text{STT} \longrightarrow \text{LLM} \longrightarrow \text{TTS} \longrightarrow \text{LiveKit Out}
\end{aligned}
\end{equation}
A \texttt{UserBotLatencyObserver} continuously profiles user-to-bot conversational latency across stages.
\textbf{Session Supervisor:} A FastAPI daemon (port 8021) spawns per-room workers via HMAC-SHA256 signed session descriptors from the Gateway, enforcing a 45~s join timeout and managing room lifecycle.
\textbf{Alternate Worker Runtime:} Legacy standalone \textbf{LiveKit Agents} ($\ge 1.6$) is retained as an MCP-compatible fallback, mutually exclusive with Pipecat per room.
\textbf{Microservices Architecture:} Two FastAPI microservices divide application logic: (1) \emph{Assistant Gateway} (port 8020) manages accounts, sessions, enrollment, and signed LiveKit tokens; (2) \emph{Matcher API} (port 8011) stores public CKKS contexts and encrypted voiceprints in SQLite, evaluating ciphertext-only squared Euclidean distances without accessing raw audio, plaintext embeddings, secret keys, or plaintext scores.

\textbf{Voice Activity Detection (Silero VAD v5).} The model computes speech probabilities per 20~ms frame from incoming 16~kHz 16-bit linear PCM audio frames:
\begin{itemize}
    \item \textbf{Vocal Onset:} Speech is confirmed once frame probability satisfies $p \ge 0.7$ continuously for at least 384~ms (\texttt{VOICE\_VAD\_MIN\_SPEECH\_SECONDS=0.384}).
    \item \textbf{Vocal Offset:} Silence is recognized after 650~ms below threshold (\texttt{VOICE\_VAD\_SILENCE\_SECONDS=0.65}), with a hard maximum utterance cap of 20~s (\texttt{VOICE\_VAD\_MAXIMUM\_SECONDS=20}).
\end{itemize}

\textbf{Turn-Taking and Endpointing (Smart Turn v3).} Conventional fixed-silence timers prematurely interrupt speakers during natural cognitive pauses. Who-Speak-AI integrates Smart Turn v3 (\texttt{smart\_turn\_v3.onnx}) running on ONNX Runtime ($\ge 1.17$). When Silero signals a silence boundary, Smart Turn ingests the buffered audio and runs an end-of-turn classifier evaluating prosodic, acoustic, and linguistic completion cues. If the turn is predicted to be ongoing, cut-off is suppressed for up to an additional 2~s (\texttt{VOICE\_SMART\_TURN\_MAX\_WAIT\_SECONDS=2}). An in-memory RMS turn buffer (\texttt{LocalSpeechTurnBuffer}, amplitude threshold 0.012) provides a deterministic fallback.

\textbf{Speech-to-Text (PhoWhisper).} User speech is transcribed locally using \texttt{faster-whisper} with the \texttt{vudang449/\allowbreak PhoWhisper-small-ct2} checkpoint---a Vietnamese-specialized CTranslate2 model running in \texttt{int8} quantization on CPU (\texttt{VOICE\_WHISPER\_MODEL}, \texttt{VOICE\_WHISPER\_COMPUTE\_TYPE=int8}). Operating at 16~kHz mono with a forced language prior (\texttt{language="vi"}), the engine decodes audio directly in system memory without dispatching waveforms or transcripts to any external cloud service.

\textbf{Conversational Reasoning (OpenAI LLM).} Clean transcripts are dispatched to OpenAI via the streaming Responses API. The model is configured via \texttt{OPENAI\_MODEL} (default \texttt{gpt-5}). The cognitive core is strictly decoupled from Voice Verification data:
\begin{itemize}
    \item \textbf{Deterministic Capability Policy:} Dialogue policy is governed by \texttt{ConversationSupervisor} and \texttt{SupervisorPolicy}. The LLM is restricted to generating natural-language text. Tool execution orchestrated explicitly to verify user and inject only accessible capability signatures (\texttt{allowed\_tools}).
    \item \textbf{Token Chunking:} To minimize Time-to-First-Audio (TTFA) latency, text is cleanly partitioned at the nearest preceding word boundary and sent to TTS, then LLM generation with audio synthesis.
\end{itemize}

\textbf{Neural Speech Synthesis.} Audio vocalization uses a dual-engine architecture:
\begin{itemize}
    \item \textbf{Primary Engine - ZeroTTS:} A local neural TTS model running under ONNX Runtime with multi-threaded inference. Using preset Vietnamese weights (\texttt{maichi}), it synthesizes 48~kHz mono audio with a 150--250~ms startup buffer.
    \item \textbf{Fallback Engine - EdgeTTS:} If ZeroTTS encounters initialization or hardware failures, the pipeline dynamically fails over to Microsoft Edge-TTS, streaming Azure's {\texttt{vi-VN-HoaiMyNeural}} voice.
\end{itemize}

\textbf{Biometric Feature Extraction (RawNet3).} Biometric identity verification is powered by our fine-tuned RawNet3 model (16.28M parameters). RawNet3 processes raw 16~kHz mono PCM waveforms ($\ge 3.0$~s) directly in the time domain:
\begin{enumerate}
    \item \textbf{Time-Domain Feature Extraction:} A parameterized Sinc-convolution filterbank replaces standard Short-Time Fourier Transform (STFT) or log-mel spectrogram computation, preserving phase information.
    \item \textbf{Deep Representation:} Filterbank outputs pass through a modified Res2Net architecture enhanced with Alpha-Feature-Map Scaling (AFMS) and Squeeze-and-Excitation (SE) channel blocks.
    \item \textbf{Embedding Normalization:} The model outputs a continuous 256-dimensional speaker embedding $\mathbf{v} \in \mathbb{R}^{256}$, normalized under the $L_2$-norm:
    \begin{equation}
        \mathbf{v} \leftarrow \frac{\mathbf{v}}{\|\mathbf{v}\|_2}, \quad \|\mathbf{v}\|_2 = 1
    \end{equation}
\end{enumerate}

\textbf{Encrypted Matching \& Hardware Key Protection.} The candidate embedding $\mathbf{v}$ is verified under TenSEAL's CKKS homomorphic encryption scheme ($N=8192, Q=[60,40,40,60], \Delta=2^{40}$). The secret key $\text{sk}$ is sealed inside the operating system keychain via Python \texttt{keyring} under service \texttt{who-speak.voice-he}. During verification, the Matcher API evaluates the homomorphic inner product $\llbracket s \rrbracket = \llbracket \mathbf{u} \rrbracket \odot \mathbf{v}$ over encrypted reference vector $\llbracket \mathbf{u} \rrbracket$. The client or agent decrypts $s = \text{Dec}_{\text{sk}}(\llbracket s \rrbracket)$. Verification succeeds if:
\begin{equation}
    s \ge \tau \approx 0.657 \quad (\text{configurable via } \texttt{VOICE\_SV\_THRESHOLD})
\end{equation}

\textbf{Audio Gate Isolation (\texttt{AuthRouterProcessor}).} \texttt{AuthRouterProcessor} is the \emph{first} processor in the Pipecat pipeline, positioned before Silero VAD and Whisper STT. In phases \texttt{CAPTURING}, \texttt{PROCESSING}, and \texttt{WAITING\_FOR\_RESUME}, incoming audio frames are consumed or discarded by the router and never forwarded downstream. Only when the phase is \texttt{IDLE} or \texttt{CONVERSATION\_READY} (and a brief resume-guard window has elapsed) does the router forward frames to VAD and the conversation pipeline. This guarantees that the spoken authentication phrase is never processed by VAD, never transcribed by Whisper, and never ingested by the LLM.

\textbf{Policy-Gated Tool Execution.} System capabilities are divided into public utilities accessible in guest mode and protected personal tools (e.g., private calendar access). Guest users can freely engage in general-purpose conversation; privileged tool calls require $\text{AuthState} = \texttt{AUTHENTICATED}$. Unauthenticated invocations trigger a voice challenge. After the challenge result is available, the user must explicitly press \emph{Resume} or \emph{Continue as Guest}---this action opens the conversation ingress. Upon successful cryptographic verification ($s \ge \tau$), a session authorization TTL (default 5 minutes) is activated, permitting deterministic tool execution. The calendar backend is \texttt{MockCalendarProvider} when \texttt{MCP\_PROVIDER=mock}, or \texttt{GatewayCalendarProvider} (proxying to a local or Google MCP server) when \texttt{MCP\_PROVIDER=local} or \texttt{mcp}.

\begin{warmbox}[title=Audio Gate Isolation Boundary]{Zero-Leakage Security Boundary}
A critical security vulnerability in voice-driven assistants is ``passphrase leakage,'' where sensitive authentication speech is transcribed by ASR into dialogue history. Who-Speak-AI eliminates this via \texttt{AuthRouterProcessor}: challenge audio is intercepted at the WebRTC transport boundary before VAD or Whisper STT. Challenge frames are routed strictly to RawNet3 and CKKS matching, guaranteeing zero biometric or linguistic leakage into LLM contexts.
\end{warmbox}

\subsection{Privacy-Preserving Voice Authentication}\label{subsec:app-privacy}
\subsubsection{CKKS Scheme Formulation}
Who-Speak-AI implements the Cheon-Kim-Kim-Song (CKKS) cryptosystem \cite{cheon2017homomorphic} via the TenSEAL library \cite{tenseal2021}. CKKS supports homomorphic addition and multiplication on vectors of complex numbers, making it well-suited for fixed-dimensional continuous embedding spaces.

The cryptosystem is configured with polynomial modulus degree $N = 8192$, coefficient modulus bit sizes $Q = [60, 40, 40, 60]$, and scaling factor $\Delta = 2^{40}$. This parameter set guarantees 128-bit post-quantum and classical security while accommodating the multiplicative depth required for inner product evaluation.

\subsubsection{Encrypted Cosine Similarity Evaluation}
Let $\mathbf{u} \in \mathbb{R}^{256}$ denote the enrolled reference embedding and $\mathbf{v} \in \mathbb{R}^{256}$ denote the candidate verification embedding extracted by RawNet3. Both vectors are $L_2$-normalized prior to encryption:
\begin{equation}
    \|\mathbf{u}\|_2 = 1, \quad \|\mathbf{v}\|_2 = 1 \implies \cos(\mathbf{u}, \mathbf{v}) = \mathbf{u} \cdot \mathbf{v} = \sum_{i=1}^{256} u_i v_i
\end{equation}

During enrollment, the client generates a public context containing the public key $\text{pk}$, relinearization keys $\text{rlk}$, and Galois rotation keys $\text{gk}$, while retaining the secret key $\text{sk}$ in the OS keychain. The reference vector $\mathbf{u}$ is encrypted into ciphertext $\llbracket \mathbf{u} \rrbracket \leftarrow \text{Enc}_{\text{pk}}(\mathbf{u})$ and transmitted to the Matcher service.

During verification, the Matcher API computes a homomorphic squared Euclidean distance between the stored enrolled ciphertext $\llbracket \mathbf{u} \rrbracket$ and the candidate query ciphertext $\llbracket \mathbf{v} \rrbracket$:
\begin{equation}
    \llbracket d \rrbracket = (\llbracket \mathbf{v} \rrbracket - \llbracket \mathbf{u} \rrbracket) \cdot (\llbracket \mathbf{v} \rrbracket - \llbracket \mathbf{u} \rrbracket)
\end{equation}
where subtraction and dot product are applied homomorphically in ciphertext space. The encrypted scalar $\llbracket d \rrbracket$ is returned to the trusted client or agent supervisor, which decrypts:
\begin{equation}
    d = \text{Dec}_{\text{sk}}(\llbracket d \rrbracket)
\end{equation}
Verification succeeds if $d \le \tau_{d}$, corresponding to threshold $\tau \approx 0.657$ on the underlying cosine similarity space (\texttt{SV\_THRESHOLD ~ 0.65653}; configurable via \texttt{VOICE\_SV\_THRESHOLD}). At no point does the Matcher observe plaintext embeddings, raw audio, $\text{sk}$, or the plaintext score $d$.

\begin{warmbox}[title=Homomorphic Zero-Trust Guarantee]{Cryptographic Protection Guarantee}
Traditional systems must decrypt biometrics into server memory before computing distances, creating an exposure window. Under Who-Speak-AI's CKKS architecture, the Matcher API receives only ciphertexts and public context---it never receives raw audio, plaintext embeddings, the secret key $\text{sk}$, or the plaintext score $s$. Note that the trusted local voice-auth service does hold the waveform and embedding transiently during extraction and encryption; the zero-knowledge guarantee applies specifically to the untrusted Matcher microservice boundary.
\end{warmbox}
